# IPv4 打洞检查与修复

当前客户端用同一个 UDP socket 向协调服务器和队友发包。服务器从认证心跳的来源记录公网地址与端口，通过成员列表交换给双方；双方持续发送带认证的探测包。

2026-09-27 检查发现，旧实现仅向服务器告知的端点回包，没有使用已收到探测包的真实来源。遇到不同目的地对应不同公网端口的 NAT，可能错过本来能建立的连接。成员同步还会不断覆盖端点。

修复后的行为：

- 通过 HMAC 验证的 IPv4 探测请求，直接回复实际来源。
- 向新来源发送随机挑战，收到来自相同地址与端口的正确应答后，才将其用于游戏数据。单纯重放签名包不能切换端点。
- 已验证端点持续收到有效流量时，保留该端点；10 秒没有来包，则回到服务器提供的端点继续尝试。
- 新房间清除旧端点和待验证挑战。抓包记录 `ipv4_endpoint_validated`，便于验证实际是否采用了新端点。

本机 `capture-20260927-222440-7eac6c.jsonl` 中，一条 IPv4 边有双向探测；另一条边发出 41 次探测，没有任何 IPv4 来包。这只能说明本机没有观察到回复，不能单凭此确定对方的 NAT 类型，也不能证明本次故障由上述缺陷引起。日志中手动选择 `ipv4` 不代表实际打通。

进一步调查需要双方同一时间段的抓包，核对双方发出的端点和实际收到的来源。后续可采用多个候选端点、不同外部目的地的映射检测、协调重试；对双方严格过滤且目的地相关映射的情况，仍需要中转。

参考：[RFC 8445 的 peer-reflexive candidates 与 triggered checks](https://www.rfc-editor.org/rfc/rfc8445.html)、[RFC 5128 的 UDP 打洞限制](https://www.rfc-editor.org/rfc/rfc5128.html)。当前实现借鉴来源验证机制，并非完整 ICE 协议实现。
